## Proposed field and join contract

All helpers, new fields and tests in this section are proposals.

| Concern | Proposed behavior and exact edit site |
| --- | --- |
| Locality preservation | In `_normalise_tmr`, retain `road_summary.locality` verbatim as `locality` and keep the established `suburb` consumer field populated from current locality, falling back to legacy `road_summary.suburb` when missing/blank. Do not overwrite a nonblank current label with a legacy alias. In `_normalise_ims`, retain original suburb/locality values separately when supplied and apply the documented current/legacy precedence. Record originals before whitespace comparison. |
| Road aliases | `_normalise_ims`: prefer current `road`, then `road_name`, then `ROAD_NAME` for nonblank values. Keep normalized `road_name` as the existing consumer field without changing the text. Preserve lowercase/uppercase description, suburb and ID aliases, including valid numeric ID zero (use presence checks rather than truthiness). |
| Dates | `_normalise_ims`: use `duration.start`/`duration.end` when the respective keys are present, then flat lowercase/uppercase legacy fields when absent. An explicit current null end means unknown and must not resurrect a stale legacy end. Preserve date strings and timezone offsets. Do not expand recurrence/history behavior. |
| Impact and event fields | `_normalise_ims` should match the existing TMR normalized keys for `event_type`, `event_subtype`, `event_due_to`, `impact`, `advice`, `information`, `status`, `last_updated`, `provided_by`, `provided_by_url`, `url`, `web_link`, when present. Reuse `_flatten_impact` so nested objects never print as dictionaries. No fabricated values for absent fields; keep a consistent nullable contract. |
| Geometry | Extract `_point_coords(geometry)` in `scrape/road_closures.py`; use it from both normalizers. Support direct Point and a Point anywhere in `GeometryCollection.geometries`; LineString/empty/missing geometry returns no Point. Do not centroid, geocode or infer coordinates. Keep raw feature, icons and unrelated fields out of normalized JSON. |
| Canonical membership | In `build_graph`, consume scope 1's `_suburb_key`, `suburb_labels` and list-valued `closure_suburb_keys`. Preserve scalar raw `suburb`/`locality` and existing published `closure_suburbs` shape; add internal membership rather than silently replacing a string with an array. `render_suburb` and `render_division` must use those memberships. |
| Multi-locality matching | Add `_traffic_locality_keys(raw, known_keys)` in `build/build_site.py`. Freeze `known_keys` from existing structured project/consultation/DA locality labels before traffic token matching; never treat prose as locality evidence. Accept a single exact canonical label; for TMR's observed slash-delimited format only, trim/collapse each token, match exact known keys, discard blank/unknown tokens and dedupe keys. For IMS use its structured single suburb label; do not introduce speculative delimiter rules. Keep compound raw text unchanged and never publish it as a new suburb page. No comma/`and`/newline splitting or substring/fuzzy matching. |
| Known single locality | Preserve the existing ability to retain a structured single source locality; join if it matches a canonical place. An unknown single label remains available as source text with no guessed edge under the conservative traffic join rule. This proposed stricter join rule needs review because the current graph seeds new suburb pages from any closure label. |
| Event identity | Keep event rows separate and the existing `c{i}` graph alignment. Do not deduplicate by numeric ID alone across feeds or by prose. A division sees one occurrence even when several named localities reach it; each matching suburb sees that occurrence once. Test reordering to verify graph/render alignment. |

Structured project/consultation/DA labels are currently gathered in different phases of `build_graph`. Move the closure-locality matching phase after that structured gazetteer is ready and before meeting/news extraction. Road extraction can remain in the existing closure pass. This prevents 816297's compound string from becoming its own gazetteer entry and ensures Gailes/Redbank/Riverview are resolved through the same scope 1 keys. Scope 1 alone must not start splitting compound labels.

## Static display and provenance boundary

Propose a small shared `_traffic_details_html` helper in `build/build_site.py` for optional retained facts and source links. Wire it into the existing impact sections in `render_index`, `render_street`, `render_suburb` and `render_division`; use retained event/provider/dashboard links in `build_project_timeline` as well. Show the source road/locality text, event type, flattened impact, advice and supplied start/end as readable escaped HTML with source attribution. Label missing end dates as unknown/omit the optional value rather than implying the road has reopened. Avoid duplicating a row when an event names several localities.

Use existing record links (`url`/`web_link`) and `provided_by`/`provided_by_url` where available, with a clearly labelled Council dashboard fallback. Credit the observed provider; distinguish the feed identifier from authorship. Do not hard-code TMR authorship for Council-originated proxy events or label IMS as covered by a TMR dataset grant. No licence badge or blanket CC BY wording is authorized here.

The earlier report records unresolved QIT Plus IMS rights and separate TMR dataset evidence. **Attribution is not a permission decision.** The human must resolve the source-specific publication/fixture policy before merging or publishing newly retained source content; this task does not decide rights, contact providers or rewrite global licence claims. If public fixture retention is not approved, use synthetic schema cases temporarily and keep the saved real-sample acceptance explicitly pending. Icons, permit metadata, full source payloads and unrelated fields are unnecessary.

Keep existing snapshot timestamps and freshness guards intact. Adding snapshot context to every entity section is a separate proposed follow-up, not silently included here. Do not broaden failure recovery or empty-feed semantics while fixing field mapping; the current per-feed exception behavior remains a separate risk.
