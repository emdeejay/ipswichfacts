## Outcome and boundaries

Residents should reach one existing suburb URL containing all records attached to equivalent whitespace/case labels. Keep each source label verbatim in its record. Introduce comparison keys for joins; do not rewrite source data, project identities or pinned URLs.

Only trim leading/trailing whitespace, collapse whitespace runs and compare with `casefold()`. No spelling correction, fuzzy matching, geocoding, splitting compound locality labels, new source, historical rescrape or development-application schema expansion. Unknown and multi-locality labels remain intact. Source-permission policy is a separate decision; this plan does not resolve it. Static HTML, unofficial framing, source links, consultation metadata restrictions and the DA whitelist remain requirements.

## Proposed implementation contract

These are proposed changes, not descriptions of existing helpers or schemas.

1. Add `_suburb_key(label)` near `slugify` in `build/build_site.py`: return the whitespace-collapsed, stripped, casefolded string, or no key for null/blank input. Keep punctuation and compound labels. Do not reuse `_norm`, which also removes punctuation, and do not change `slugify` globally.
2. In `build_graph`, assemble a canonical key-to-display-label and key-to-existing-path mapping. Prefer an already clean source label; break ties deterministically, independently of input order, with the 11 existing labels/paths above pinned by regression expectations. Retain original source fields and existing public scalar label mappings. Add internal canonical membership maps rather than changing record fields or the published `mentions.json` shape silently. Proposed names: `suburb_labels`, `suburb_slugs`, `project_suburb_keys` and `closure_suburb_keys`; use a list of keys per closure, initially zero or one **atomic** label, so the traffic follow-up can add conservative multi-locality membership.
3. Use the key for `suburb_meeting_items`, `suburb_news_items`, `suburb_consultations`, `suburb_das` and `suburb_divisions`. Deduplicate references per canonical bucket by source identity: project input row ID for the saved sample, meeting `(slug, anchor)`, news/consultation `slug`, DA `application_number`, closure occurrence `c{i}`. Do not merge distinct projects sharing a reference or URL. Normalize extractor results back through the same key; build its gazetteer from canonical labels and collapse whitespace for matching without changing stored prose. Exclude the canonical `ipswich` key from prose matching under every label variant.
4. Update `render_suburb` to select records by canonical membership and use one display label/path. Update `render_division` and place links in `render_project`, `render_meeting`, `render_news_post`, `render_consultation`, `render_list` to resolve the same canonical path. Adapt `write_site` JSON emission: publish one canonical display label per suburb in `suburbs.json`, translate internal keys back to labels for existing `mentions.json` fields, preserve raw project/closure/DA/consultation record labels. Verify embedded `_WIDGET_JS` search links resolve for retained raw labels, including case variants. Avoid unrelated search/payload changes.
5. Stage page output/preflight inside `write_site` before clearing the destination. Index by the resolved output target. One identical body with compatible date metadata may be emitted once; differing body or conflicting metadata for the same target raises a diagnostic identifying path and source identities. Append a sitemap URL once. Do not fix a conflict by taking the first/last body, changing published slugs, or hiding the duplicate in `_sitemap`. Leave the previous output intact on preflight failure. No deployment/workflow change is part of this proposal.

The page-path mapping is separate from source identity: for the observed groups canonicalization preserves every existing suburb URL. A newly encountered equivalence group with divergent existing paths or an unrelated slug collision must stop for review rather than invent a URL migration.

### Acceptance tension requiring a human decision

The saved 65 Ipswich records have **65 distinct IDs but 64 project slugs**. IDs **268 and 270** share `brisbane-street-road-resurfacing-270` and render different project HTML. Across all 456 project rows, there are **450 slugs**, with differing rendered bodies at four repeated paths:

- `/project/redbank-plains-road-road-resurfacing-303/` (four records).
- `/project/brisbane-street-road-resurfacing-270/` (two records).
- `/project/robertson-road-road-resurfacing-293/` (two records).
- `/project/lobb-street-road-safety-improvements-churchill/` (two records).

This was verified using `render_project` with the project-only graph, not inferred from sitemap counts. A global conflicting-write guard therefore rejects even the saved Ipswich end-to-end build. Existing registry uniqueness tests cannot detect two input records resolving to one registry identity.

**Recommendation:** retain the global fail-visible requirement and pinned URLs, and commission a separate bounded decision on representing conflicting project records before expecting a successful complete current-data build. Suburb rendering/membership can be tested independently meanwhile; that alone does not satisfy the full-build acceptance criterion. An alternative would be explicitly narrowing the guard to suburb writes, but that changes the acceptance interpretation and needs approval. This plan neither chooses project aggregation/identity changes nor claims the tension is resolved.
