## Accepted scope

Conservative alias handling for the five existing street paths whose labels differ only in capitalisation or punctuation: `anzac-day-parade`, `augustines-drive`, `brisbane-street`, `nicholas-street`, `tallegalla-two-tree-hill-road`. Keep every source reference, raw label and published URL. Update the graph, static pages and exported/search links consistently. Out of scope: fuzzy geography, new sources, registry migration, guard weakening, workflows, merge and deployment. Ambiguous identity is refused, not guessed.

Revision 2 (29 October 2026) adds one P2 only: a line-wrapped single suburb name ("Springfield\nLakes" beside "Springfield Lakes") must not be classed as a composite multi-locality label, while the known composites stay out of prose matching. Allowed edits: `build/build_site.py`, `tests/test_suburb_joins.py` and this record. The optional display-label P3 is out of scope.

## Current handoff — revision 2 repair, 29 October 2026

**Ready for Codex and Claude review. The P2 is fixed; no other change.** No merge or deployment. No Done claim: production acceptance still needs current inputs that pass the strict count and freshness guards.

**Defect.** `_composite_suburb_keys` marked a whole suburb key composite when *any* raw variant spanned two nonempty lines. Adding a project labelled `"Springfield\nLakes"` next to a clean `"Springfield Lakes"` therefore removed Springfield Lakes from the prose gazetteer. A news post and a meeting item titled "Springfield Lakes update" then got empty suburb lists and vanished from the suburb page and the division's meeting and news mention sections. Page path and direct project joins were unaffected.

**Fix (`build/build_site.py`).** A line break is composite evidence only when *every* variant of the key is multi-line, i.e. no source writes that name on one line. A label made entirely of other known suburbs stays composite regardless (unchanged `splits` rule). The rule is a pure function of the variant set, so it doesn't depend on input order. Raw labels, display-label choice, slugs, URLs, registry and the output guard are untouched.

Why this boundary: in the cached production inputs, all five multi-line suburb values are genuine lists (`Bellbird Park / Redbank Plains`, `Collingwood Park / New Chum / Redbank Plains`, `Collingwood Park / Redbank / Redbank Plain / Bellbird Park`, `Springfield Central / Augustine Heights`, `Springfield Central / Springfield Lakes`), and none of them is ever written on one line. All stay composite.

**Regression.** `test_line_wrapped_single_suburb_still_matches_prose`, two cases: clean label only, and clean plus `"Springfield\nLakes"`. Each runs in both input orders and checks the composite set (the two known composite shapes included), `news_suburbs`/`meeting_suburbs`, the suburb buckets, and the news and meeting links on the suburb page and on the division page. `test_composite_suburb_values_are_not_matched_in_prose` is unchanged and still passes.

## Implementation handoff — 26 October 2026

State at `5e63614` (history; the repair section above supersedes it where they differ, notably row order on merged pages and search). The complete cached-data structural build succeeded. No merge or deployment.

### What changed (`build/build_site.py`)

- `_street_key(label)` is a comparison-only key: casefold, with straight and curly apostrophes and extra spacing removed. Nothing else is treated as the same street. Abbreviations are already expanded by the extractor.
- `_street_catalog` groups the extracted labels by key. Each group gets one display label for its page, chosen deterministically: clean spacing, then capitalised words, then fewest capitals, then lexical order. The chosen labels are `Anzac Day Parade`, `Augustine's Drive`, `Brisbane Street`, `Nicholas Street` and `Tallegalla Two Tree Hill Road`. The page path is unchanged (`slugify` of any spelling in the group).
- `_validate_street_paths` runs next to the suburb check, before the output plan. It refuses (1) one key whose spellings would slugify to different paths, and (2) two different keys on one path. Either way it raises before prior output is touched. The `_OutputPlan` guard is unchanged.
- In `build_graph`, the street-keyed buckets (`street_meeting_items`, `street_news_items`, `street_consultations`, `street_das`) are merged per page in sorted spelling order. In merged groups only, a source item that names both spellings appears once (identity: meeting slug + anchor, news slug, consultation slug, DA number). Single-spelling buckets are passed through unchanged. `related_streets` compares by page, so a street is never its own connected street. New graph keys: `street_labels`, `street_slugs`, `street_variants`. `graph["streets"]` (and `data/streets.json`) lists one label per page.
- Per-entity lists keep each source's own spelling: `project_streets`, `project_record_streets`, `closure_streets`, `meeting_streets`, `news_streets`, `consultation_streets`, and so `mentions.json`. Project, meeting, news and consultation pages still show the record's own spelling, and the link resolves to the shared path.
- `render_street` matches projects and closures by page. When it gathers more than one spelling it adds one factual line: "Council's records write this name more than one way: … They differ only in capitalisation or apostrophes, so this page gathers them." Pages with a single spelling get no new markup.
- The project page's street-matched meeting items and the project timeline's closure match both compare by page. They agree with the street page they link to.
- In the widget search index, a street's haystack also includes its apostrophe-free form. "augustines drive" and "augustine's drive" both find the one page.
