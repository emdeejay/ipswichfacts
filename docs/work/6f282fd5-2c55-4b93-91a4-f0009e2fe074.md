### What changed (`build/build_site.py`)

- `_project_record_groups(projects)` groups records by their pinned slug. Byte-identical rows count as one record; every other row is a distinct record. Order is `(numeric id, canonical JSON)`, so feed order has no effect. Each record gets the anchor `record-<id>`, with a `-2`, `-3` suffix only if one id repeats with different content (not seen in the data).
- `write_site` writes each project URL once. A one-record group goes through the unchanged `render_project`. A larger group goes through `render_project_group`. The `_OutputPlan` conflict guard is untouched and still rejects every other duplicate write before touching prior output.
- `render_project_group`:
  - Page-level `<title>`/`h1` is the published name. When names differ, it is our display text joining the names with ` / `.
  - Meta and og descriptions state only the record count and the published name(s).
  - Each record gets its own `<section class="project-record" id="record-<id>">` holding its own name, phase, suburb, ref, last-updated date, description, status, what-to-expect, wording discrepancy, division, managed-by, Council notices, streets and source link.
  - Links shared across the group are split by how they were matched. **Matched by project name(s)** holds the funding (with `money_disclaimer`), the budget/meeting/news timeline, meetings and news. **Matched by street** holds current road impacts and meeting items that mention streets named in one or more records. Both sections say they don't belong to any one record.
  - There is no structured data (JSON-LD), and the page never states a combined status, phase or date.
- Fixed these losses where slug-keyed graph values were overwritten (last writer wins):
  - `project_record_streets` holds streets per record occurrence. Street pages, works notices and connected streets now use each record's own streets. Previously every grouped record was attached to whichever record was last in the feed.
  - `project_streets[slug]` (exported in `mentions.json`, same slug → list shape) is now the union for grouped slugs.
  - `project_cores` keeps every eligible name core per slug (a reviewer reproduced order-dependent loss when names differ). Capital-works stage checks use every stage tag on the slug.
  - Meeting and news "projects discussed" links use the group title and link once.
- Project links on the project lists, phase lists, road-impact wording page, home page, suburb, division and street pages point grouped records at their own section (`/project/<slug>/#record-<id>`). Single-record links are unchanged. The widget's search index (`data/projects.json`, raw and unchanged) still lists every record, linking to the shared page.
- Sitemap `lastmod` for a group is the latest record update. It is page modification metadata only and never appears as a project fact.

Known limits: Council's map `id` is positional and can be recycled (see `_project_registry_key`), so `#record-<id>` anchors are only as stable as Council's ids. List pages keep their existing feed-order tie-breaking between equal names; the links they carry don't depend on it.
